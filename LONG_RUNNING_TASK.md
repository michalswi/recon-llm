# Long-Running Task Behavior

> **Status: TODO — long-running task improvements remain.** The behavior below describes the current implementation, not a proposed or completed solution to every long-running-task limitation.

How recon behaves when given a long-running task, based on the current worker, runtime, terminal, and API implementations.

- **Iteration budget**: 30 iterations per execution segment by default, configurable with a positive `RECON_MAX_ITERATIONS` value. Unset, invalid, zero, or negative values use the default. Each run captures its limit as `maxIterations`. `iteration` remains the lifetime count for auditing; `segmentIteration` tracks the current segment and resets after clarification, revision, or explicit continuation. Automatic retries and critic revisions do not renew the segment budget.
- **Iteration-limit pause**: exhausting the budget sets `waiting_continue`, not `limit_reached`. The terminal offers continue [c] or stop [s]. API clients explicitly use `POST /api/agent/runs/{id}/continue` (no body) or `/cancel`; `/feedback` and `/approve` cannot resume this state. Continuing renews the iteration and time budgets without discarding events, findings, plans, requirements, or attachments. Paused runs retain background jobs and are not eligible for API retention eviction. Stopping cancels the run and cleans up its jobs.
- **Wall-clock cap**: each active execution segment gets a 30-minute deadline (`agentRunTimeout`, applied via `agentRunContext`). Resuming after clarification, revision, or explicit continuation starts a fresh deadline. Waiting for user input, approval, or continuation is outside that active deadline, so the entire lifecycle can exceed 30 minutes. The active deadline remains a terminal safety limit, not a continuation prompt.
- **Model timeout**: each model request attempt uses `agentModelTimeout`, defaulting to 5 minutes and configurable through `RECON_MODEL_TIMEOUT`. The enclosing segment deadline can end it sooner. Local model-request timeouts are not retried; transient transport failures and HTTP 429/5xx responses can receive up to three attempts.
- **Foreground-command timeout**: `run_command` uses a 2-minute deadline (`agentCommandTimeout`), also bounded by the segment deadline. Command failure or timeout is recorded as an observation. This is not a strict process-tree termination guarantee: foreground execution uses `exec.CommandContext` for the shell without the process-group cleanup used for background jobs.
- **Background execution**: `run_command_bg` starts external work without waiting for completion. Jobs have a separate 1-hour timeout. They can continue while the run waits for clarification, approval, or continuation, but terminal run cleanup kills any remaining run-owned jobs, including when the run reaches `limit_reached`.
- **Worker-side waiting**: `check_job` and `get_job` wait for a running job's completion signal before returning its final snapshot. The check costs one iteration; waiting adds no model calls or iterations. Already-finished jobs return immediately. Ctrl+C, API cancellation, and the active segment deadline interrupt the wait. The worker cannot do other work during this check; perform independent actions before checking, or use `list_jobs` for an immediate overview. Repeated `list_jobs` actions still consume iterations. Waiting does not extend the wall-clock budget.
- **Context growth**: compaction targets an estimated 4096-token recent-event window, not a hard limit on the complete prompt. Even that window can exceed the target to retain the newest event. Base instructions, attachments, plans, revision history, and summaries add more context; the 768-token summary target is a model instruction, not an enforced output cap. Compaction does not extend the iteration or time budgets.
- **`limit_reached` is terminal**: deadline expiry still ends the run and cleans up its jobs. Neither `/feedback` nor `/continue` can resume this state; a new run must be started. Persisted snapshots are audit records, not automatic restart/resume checkpoints.

Summary: each segment has a configurable iteration budget and a 30-minute deadline. Exhausting iterations pauses for explicit continuation; deadline expiry remains terminal. Background-job checks wait without repeated model polling, preserving iterations while keeping cancellation and deadlines active.
